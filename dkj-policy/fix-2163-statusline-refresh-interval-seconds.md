### PLAN

#### The reported reason, verified before the repair (#2163)

The issue infers that the statusline's clock "appears to be conversation activity, not time", and asks
whether the record or only the render was stale. **The inference holds and the cause is more specific
than it says: the timer is set in the wrong unit.** `refreshInterval` is in SECONDS with a minimum of 1
(Claude Code's statusline documentation, the `refreshInterval` field, read September 19, 2026), and this
repo set `2000` -- 33 minutes -- on the reading that it was milliseconds. So the fixed timer that exists
for exactly "the main session is idle" never fired inside any real run, and the bar redrew only on the
event-driven triggers (a message sent, a turn ending), which is the 34 -> 113 jump on typing. The record
is therefore not in question and `native-capture-lib.ps1` needs no change, which is the outcome the issue
named as the good one.

The issue's own first-checked and rejected explanation (a lagging prefix) stays rejected. Nothing else
in it is contradicted.

The wrong unit was written down in more than one place -- `.claude/settings.json`, both values in
`adopt-statusline.ps1`, and the test that pinned `'2000'` -- plus one sentence in the system-administration
lens that called it a "2,000 ms interval". Repairing the setting alone would have left the test failing
the repair and the lens teaching the error.

The statusline adoption is not in any release (`v5.5.0` does not contain it), so no consumer has the wrong
value and none needs to act.

- [x] `.claude/settings.json`: `refreshInterval` 2000 -> 2.

- [x] The system-administration lens: "2,000 ms" corrected, and the unit and the measurement written down.

### DEPLOY: fix/2163-statusline-refresh-interval-seconds

The progress bar's timer was set in the wrong unit and so never fired: `refreshInterval` is in seconds,
this repo set `2000`, and Claude Code read that as 33 minutes -- so during a backgrounded gate the bar
stayed on whatever count it last drew and jumped to the true one only when the operator sent a message,
which is the moment they had stopped believing it. It is now `2`, in this repo's own settings and in what
`adopt-statusline.ps1` places, with the unit stated where the number is set and a test that refuses a
millisecond-sized value coming back. The statusline adoption is not in a released version yet, so no
consumer carries the wrong figure.

The failure it prevents, named: a released reader turning the progress bar on and finding it frozen for
the whole of every run they backgrounded, updating only when they speak. That has not happened outside
this repo, because the feature has not shipped.
