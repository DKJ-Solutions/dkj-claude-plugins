# Release notes v5.16.0 🚀

**Date:** 2026-10-07\
**Type:** Minor\
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

Release version 5.16.0

## What changed

**This release only touches BWJ stores** (`bwj-development`). Two of its four items ask you to copy the
Asana template again. Do that once, and the session check below tells you if you missed it.

### BWJ stores: copy the Asana closed-message template again

Run `adopt-bwj-development` after the update and copy `.github/workflows/asana-closed-message.yml` and
`.github/scripts/asana-closed-message.ps1` over your current copy. Until you do, your store keeps the old
behaviour on both points below:

- **The go-live block reaches the Asana task again.** When an issue closes as completed, the task now gets
  the go-live block, not just the bare closed line. On GitHub's runner the old copy could not read the
  issue's comments, so the block was dropped without a word. If the comments still cannot be read, the run
  log now says so and the bare closed line still goes out
  ([#2875](https://github.com/DKJ-Solutions/dkj-claude-plugins/issues/2875)).
- **The reopened line reads like the others:** *"GitHub issue &lt;ref&gt; **is reopened:** this Asana
  task is now back in development."*
  ([#2870](https://github.com/DKJ-Solutions/dkj-claude-plugins/issues/2870)).

### BWJ stores: a session tells you when the Asana messages cannot work

No action needed to get it. In `smartwatchbanden` and `xoxowildhearts`, session start now reports a
closed-message workflow that is missing, a copy that differs from the template your plugin ships, or an
`ASANA_PAT` secret the repo cannot see. It names the `adopt-bwj-development` step that fixes it. Until this
release, a store that skipped that step lost every closed and reopened message with no sign of it. After
this update, the check will flag your copy until you have taken the template above
([#2871](https://github.com/DKJ-Solutions/dkj-claude-plugins/issues/2871)).

### BWJ stores: the `CRO` label is retired

No action needed. An issue raised by the CRO team is now labelled like any other: its kind (`bug` or
`feature`) and its reach. `adopt-bwj-development` no longer creates `CRO`. An existing `CRO` label stays
on your repo as history, and only the repo owner can delete it, by hand
([#2869](https://github.com/DKJ-Solutions/dkj-claude-plugins/issues/2869)).

## What it is worth

- **The Asana loop from v5.15.0 now works.** The go-live block was the main reason for the closed message,
  and on the runner it was not arriving. A requester now gets it on their task without anyone pasting it.
- **Silent failure became a visible one, twice.** A failed comment read now leaves a line in the run log,
  and a store that never took the template, or lost its secret, hears about it at session start. Both
  failures cost messages for weeks without anyone noticing. Now a session catches them on its first day.
- **One less label to choose.** Filing an issue for the CRO team no longer asks for a separate
  classification, so issues from every team go through one triage path.
- **Measured cost of this release:** clock started 10:59:48. A first cut attempt was stopped during its
  lint gate, before anything was written, and restarted with this repo's standard title. The cut that ran
  (lint, all 156 suites in 211s on 22 lanes, bump, commit, tag, push) landed its release commit at
  11:04:45, **4m 57s** from the clock start, all of it blocking.
