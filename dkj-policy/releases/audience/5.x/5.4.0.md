# Release notes v5.4.0 🚀

**Date:** 2026-09-17\
**Type:** Minor\
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

Release version 5.4.0

## What changed

Most of this release repairs things that were quietly not working. Two of them meant a documented
procedure had never once run to completion. Start at the top.

### One thing to do, if you run the Shopify theme lifecycle

**You can now run `sweep-preview-themes` with `-Execute` against a store that has parked branches.**
The sweep used to delete a parked branch's only preview theme, so any store with parked work could not
safely run it at all. If you kept a temporary wrapper around the sweep to compute `-Keep` yourself, that
wrapper is what you delete — the sweep now spares every living branch's preview, not just the current
one.

### Blockers gone — update and they are simply fixed

**Your theme backup can now actually complete.** Both halves of `backup-live-theme.ps1` were broken, and
both failed cleanly enough to look like nothing was wrong:

- it stopped at step 1 of 3 from any agent or non-interactive session, because the duplicate it makes of
  the live theme did not carry `--force`, which the Shopify CLI requires outside CI. The message
  correctly said the previous backup still stood, so a store following the documented release procedure
  simply never got a baseline while every document said it had one;
- its verify step could never pass on Shopify CLI 4.8.0 and later, refusing with *"Could not read the
  LIVE theme's file count"*. Verification no longer depends on `theme info --json` carrying a `files`
  array.

**`update-plugins` works on a Windows/npm-global install.** Both the marketplace refresh (step 1/3) and
the per-plugin update (2/3) used to fail outright on that install shape.

**A plugin installed machine-wide no longer stays behind release after release.** `update-plugins` and
`plugin-versions` took `--scope project` regardless of how a plugin was actually installed; the CLI
refuses a scope a plugin is not installed at, so the run ended red and the plugin never moved. Both now
read the scope from the install record, and the receipt prints the command that was really run.

**Commands you paste off these pages now work on Windows.** Every printed command — and every `Get-Help`
example in the plugin-carried scripts — used to depend on an execution-policy prerequisite no page
mentioned, and the failure arrived looking like a security error.

**Cloning this repository on Windows works again.** A stray file with a name Windows cannot check out had
reached `main`; new clones are unaffected. The name stays in history, which no gate can reach.

### New, and all of it opt-in

**A budget on your always-on document path.** Your `CLAUDE.md` and everything it imports can now be held
to a ceiling that applies in *your* repo rather than in the repo that ships the tooling. Adopting it is
one optional seam (`Get-AlwaysOnBudget`, 100,000 bytes if you say nothing) plus a scaffolded runner. A
repo already over the ceiling is held to its own history and converges on it, so you do not meet a red
check you cannot clear. Nothing runs until you adopt it.

**A CI skeleton for a repo with no CI at all.** "Make one check required" was advice with nothing behind
it if you had no workflow to require. The skeleton gives you one; its body stays deliberately empty, so
it asserts nothing about what your checks should be.

**`claim-issue` catches one more duplicate.** Its parked-fix scan now also warns when a branch name and
an issue title share tokens — the case where the same fix gets built twice.

**If you run `dkj-policy-bwj` in a store repo:** closing a CRO issue now posts a paste-ready Asana
comment instead of leaving you to compose one, the CRO team has a documented reporter label so its
tickets are filterable, and a new skill builds and publishes the minor backlog page for a colleague.
All three are additive; nothing you do today changes.

### Quieter, no action needed

- **`claude-review` no longer goes red when the account is out of quota.** It stays red for everything
  else, where there is something you can actually do. Seven issues had been filed against this one check;
  a signal that fires on every pull request is not a signal.
- **`dkj-policy`'s README row for `dkj-policy-bwj` now states four chapters and four skills**, not three
  and two. Worth re-reading before you enable it: one of the chapters it never mentioned deletes themes
  from a live store's estate.
- **The ticket-work step in `CONTRIBUTING-portable.md` states its real scope.** It described a
  two-repo reach that had already widened.
- **A twelfth PowerShell trap is documented:** `@(...)` throws on a `List[object]`. One ordinary edit
  away in any repo that builds one.
## What it is worth

**A documented safety net that had never once run.** Both BWJ store repos name `backup-live-theme.ps1`
as the closing step of a release cut, and both halves of it were broken — the duplicate refused from any
non-interactive session, and the verify step could not pass on the CLI version in use. Every failure was
clean and correctly reported that the previous backup still stood, so nothing looked wrong. The exposure
was a live storefront with no verified baseline while the procedure said there was one; that is now a
real backup rather than a documented intention.

**A theme estate that could not be cleaned.** The preview sweep could not safely be run against a store
with parked branches, so spent preview themes accumulated against a finite ceiling, and one store built
a temporary wrapper to work around it. The sweep runs now and that wrapper can go — one less piece of
local machinery to keep in step with the plugin it wraps.

**Plugin updates stop being handwork.** On a Windows/npm-global install, `update-plugins` failed at its
first two steps; where a plugin was installed machine-wide, it stayed behind release after release while
the run ended red. Both are fixed, which is what makes "run one command to be current" true rather than
aspirational — and it is the difference between a colleague updating their own tools and asking a
developer to do it.

**One check is a signal again.** `claude-review` went red on every single pull request when the
organisation hit its monthly spend limit — no credential to rotate, no re-run that helps. Seven issues
had been filed against that one check. It now stays red only where somebody can act, which is the whole
value of a red check.

**A ceiling that holds where the weight actually is.** The always-on document budget applies in the
adopting repo rather than in the repo that ships the tooling, so the cost of instruction documents is
bounded by the team that pays it.

## What this release cost

Measured, not estimated. The clock started at 10:15:29 and this section was frozen for its own commit
at 10:35:24 — a subtotal of **19m 55s**, all of it blocking a person.

| leg | wall-clock |
|---|---|
| the cut itself (lint gate 28s + 107 suites 451s, then notes generated, versions bumped, commit + tag) | 9m 21s |
| pushing the commit and the tag | 11s |
| rewriting the audience draft (642 lines to 120) and re-running both gates from the trunk | 10m 23s |

**The test gate is 77% of that, and it ran twice** — 451s inside the cut and 437s again before this
release-notes commit, because that commit lands directly on the trunk and the gates have to be met
somewhere. The second run was for a documentation edit. That is the fixed cost of the procedure rather
than anything this release did: releasing half as often removes exactly as much of it as making the
suites twice as fast, and needs no code.

Both runs used `-MaxParallel 4` rather than the default, which on this 32-core machine would have opened
30 lanes. The default has been killed for memory on a smaller machine, and a gate that does not *finish*
is the expensive failure here, because the cut commits and tags on `main`.

**Total: 21m 25s**, clock stopped when the last attachment landed at 10:36:54 — not at the publish, which
is one action earlier. The legs the first pass could not see:

| leg | wall-clock |
|---|---|
| committing and pushing this document to the trunk | 48s |
| publishing the GitHub Release and uploading both attachments | 42s |

**The tail is 7% of the release.** Worth recording, because the last release measured this way — at
`v4.4.0`, when the note still travelled through a pull request — had a tail of two thirds. Dropping that
PR is what moved the weight: the whole of this release is now the two gate runs and the writing, and
there is nothing left in the tail to optimise.
