# Release notes v5.3.0 🚀

**Date:** 2026-09-14\
**Type:** Minor\
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

One shared Cloudflare Worker for both BWJ stores

## What changed

### If you run `dkj-policy-bwj` (a BWJ store repo)

You can now publish both stores' release pages through **one** shared Cloudflare Worker, instead of
each store carrying `dkj-policy`'s own per-repo worker. That per-repo worker bakes the page straight
into its deployed code, so two repos deploying it under the same worker name silently erase each
other's page -- whichever deploys last wins, and both runs report success. The shared worker holds no
page content at all: every page lives in Cloudflare KV under its own key, so a redeploy from either
store can never disturb what the other published.

**No action needed today.** When you want it: answer the `Get-BwjPagesConfig` seam, create the KV
namespace, and deploy the worker once -- after that, publishing a page is a single command per store.
(`backlog` is a recognised page kind with no publisher behind it yet -- tracked separately as
[#1979](https://github.com/DKJ-Solutions/dkj-claude-plugins/issues/1979).)

### If you adopt this workflow's CI floor and your trunk has no required-check ruleset

`adopt-ci-floor.ps1` now hands you the actual command that creates the ruleset -- a ready-to-paste
`gh api` call -- instead of only telling you one is missing.

**No action needed until you run the adoption script.** When you do, and it reports a gap, copy the
printed command instead of assembling the ruleset payload by hand from the GitHub UI.

### If your repo commits the source of a durable, published Artifact

The contribution cycle now says where that Artifact's own URL belongs once its source is committed:
beside the source, read back and passed to the publish call before every republication. Without this,
editing and republishing such a source silently creates a *second*, unmaintained artifact -- the
original link keeps serving stale content, and if that page keeps its own state (a poll, a saved
document, a backlog a scheduled job feeds), the new copy starts empty with nothing erroring to say so.

**No action needed today** -- this changes what you do the *next* time you republish such a source, so
it is worth knowing about before then rather than after a page quietly goes stale.

### Documentation only

The `worktree-lane` skill now explains, in its own text, why it deliberately does not use native git
worktrees. Nothing about how the skill runs has changed.

## What it is worth

Two BWJ stores go from maintaining two separate worker deployments -- with a standing, silent risk that
publishing from one erases the other's page -- to one shared worker where that failure mode cannot
occur, at the cost of a one-time setup per store.

A consumer adopting the CI floor with no ruleset on their trunk no longer has to reconstruct the
required-check payload by reading another repo's live ruleset through the GitHub API and diffing it by
hand -- the exact detour this release closes, measured while working issue #1971.

**Timing:** the lint and automated-test gate that guards this cut ran 105 suites in 165s across 30
parallel lanes; end-to-end handling time for the cut, the release notes and publishing is recorded
below once the GitHub Release and its attachments are live.

  not an oversight.
- Nothing else was deliberately deferred at this release.
