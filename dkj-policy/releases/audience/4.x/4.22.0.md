# Release notes v4.22.0 🚀

**Date:** 2026-08-28  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

Gates that read what merges, notifications that name their sender, and two seams for the Shopify sync

## What changed

**Two scripts now refuse a run they used to let through.** Items 1 and 2 are the ones that can stop you
mid-task, so they are first. Items 3 and 4 are things you can now do; 5 and 6 arrive on their own and ask
nothing of you.

### 1. The pre-task sync refuses to stack a fifth branch on four it already opened -- act on this

`sync-main` now asks `origin` whether a sync branch from one of its own earlier runs is still standing, and
stops **before** pulling the theme if one is. **You may meet a refusal where the same command used to run
green.** That is the repair, not a regression: it was measured in a consuming repo at four unmerged sync
branches in seven days -- the newest a strict superset of the other three, two of them byte-identical --
and every one of those runs reported success, because nothing in the script had ever looked at its own
previous output.

What to do when it refuses: merge or delete the branch it names. It prints a per-branch verdict saying
whether this run supersedes each predecessor or holds paths it does not, plus the command that shows you
what that branch contains. `-DryRun` gives you the verdict without the refusal, and `-AllowStacking` runs
anyway -- for the one real case, where somebody reverted a path on live in between and the predecessor
holds the only copy.

It anchors on your own `Get-ShopifySyncBranchPrefix`, so a branch from any other source is never treated as
a predecessor, and a branch already merged does not count as standing even if your repo does not delete
merged branches.

### 2. `open-pr` refuses a finished plan while the work behind it is still uncommitted -- act on this

If your development document reads as finished but the change itself is sitting unsaved in your working
copy, `open-pr` now stops instead of opening the PR. **Commit your own work first.** The gates read that
document rather than the diff, which is exactly how a changelog entry describing an edit that never left a
working copy could merge -- and did, one release ago.

Alongside it, the lint and test gates now say out loud when they ran against a dirty tree. They judge your
working copy while the PR ships `HEAD`, so on a dirty tree a green result is not a statement about what
merges. Nothing new refuses you there; you are simply told which tree was measured.

### 3. A hand-written `Plugins:` line is refused on the branch, and repaired in the fold -- no action

If you have ever written a `Plugins:` line into your branch document's `#### Pull Request` section --
mirroring what a folded entry looks like -- your changelog has been quietly collecting two of them, one
blank line apart. Two things changed: `open-pr` and the CI gate now name that line before the merge, and
the fold strips a stray one for you and says what it dropped.

**Nothing to do.** A branch you opened before this release still folds clean -- loudly rather than
silently. The line only ever cost you a cosmetic duplicate in published output, but it was permanent once
published.

### 4. You can put a label on the Shopify sync PR without wrapping the script -- act if your CI requires one

If your CI requires every PR to carry a label, the shared sync could not open one that would merge, so you
kept a wrapper around it purely to add the label. Answer `Get-ShopifySyncPrLabels` in
`scripts/repo-config.ps1` with a label or a list of them, and that wrapper can go.

The labels go on at creation rather than in an edit afterwards -- your guardrail reads labels when it runs,
so a PR opened bare starts its first check run bare and labelling a moment later leaves you a red run to
re-trigger. The trade-off is that a label your repo does not have fails the create outright, which is the
better end to fail at: your branch is already pushed, nothing is lost, and the message says what to fix.
They go on **both** paths -- the merging one and the printed `gh pr create` line -- because the printed one
is the default, and a line without `--label` hands you the same red CI one paste later.

**No action if you leave it unanswered.** The printed line is byte for byte what it was.

### 5. Every session starts leaner, and the orchestrator's checks are a list you can work through -- no action

Chris's persona is the one document every consuming repo loads before its first assignment. This release
takes **roughly 2,240 tokens off it, on every turn in every repo**, with no rule dropped: his workflow
phase model, how he delegates parallel work, and the six inbound checks moved into a manual read on demand,
and what stayed behind was compressed.

The part you will notice by hand: those six checks used to be five paragraphs of running prose that called
themselves "the six" without ever numbering them. They are a numbered list now, so you can hold an inbound
report against them and find the fifth one.

**Nothing to do** -- you get this at your next plugin update. A specialist with no manual is untouched in
both directions.

### 6. Sylvester can tell you why a correct hook appears to do nothing -- no action

Three rules joined his hook craft, all of them for the moment you are debugging something that fires and
seems to vanish.

- **The exit code says a hook RAN; only the receiver says it ARRIVED.** Claude Code's own `Notification`
  event, for instance, produces a desktop notification by default only in Ghostty, Kitty and iTerm2 -- so
  in any other terminal a perfectly correct hook fires into nothing, and no exit code anywhere can say so.
- **A hook can be configured entirely outside your repo.** `~/.claude/settings.json` and `~/.claude/hooks/`
  are machine-wide, so a search of your project tree answers *"no hook configured"* with complete
  confidence while one runs on every turn.
- **A notification names where it came from.** If you wire a hook to a phone, one stream carries every
  machine you run, every repo checked out on each, and every session inside those -- and none of that
  context rides along on its own, because a push has no working directory, no branch and no terminal title.
  Four sessions sending the same sentence are four identical messages, and walking to each machine is the
  only way to learn which one is waiting.

**Nothing to do** -- you meet these the next time a hook goes quiet.

## What it is worth

**The gates stopped trusting the working copy, and that retires a class of silent loss.** The previous
release shipped a changelog entry describing two rules that had never been committed: the entry merged, the
release notes announced a page nobody could find, and it took a person opening the manual to notice. Both
halves are caught by a script now, before the PR opens -- one refuses, the other says out loud which tree
it measured. The risk removed is not a broken build, which announces itself loudly and cheaply; it is
published documentation that is confidently wrong, which announces nothing and reaches a customer.

**The same movement on the theme side: four right answers nobody had a reason to compare.** Seven days of
green runs had left four competing candidates for one set of theme edits, in a repo where *somebody looking
at the PR* is the entire justification for stopping before the merge. Four candidates is not that moment.
It is a refusal with a per-branch verdict now, so the pile cannot build up unseen -- and the cost of the
failure it prevents is a theme edit applied twice, or the wrong one of four applied once.

**One less wrapper to maintain, per consuming repo.** The label seam removes the last reason a repo kept its
own copy of the sync script; the body seam a day earlier removed the other. A repo on the shared script
collects every later improvement without doing anything, and a repo that forked it collects none -- which
is the whole economics of shipping this as a product rather than as a template.

**And every session everywhere starts about 2,240 tokens cheaper.** Paid once by this release, collected on
every turn in every repo thereafter, with nobody doing anything. It is the kind of saving that only exists
because the same persona is shared rather than copied.

release's own 443s to within 5%, so the gate's actual cost here is about **200s**. The suites are still the
leg that grows with the product rather than with the release, which is why they are worth watching -- they
were simply never the largest one. *(Corrected -- see below.)*

**End to end: 32m 30s**, clock stopped at 15:19:17Z when the last attachment landed. The end point is the
**last attachment**, not the publish -- the Release went up at 15:19:12Z and the assets followed 5s later,
so *"when the Release is published"* and *"when the release is finished"* are two different timestamps and
only the second one answers the question.

**The tail the first pass could not see came to 22m 01s -- more than twice the frozen subtotal -- and
almost all of it was one thing going wrong.** The gates were re-run before the notes commit, as the
direct-on-`main` route requires, and that run reported **11 of 54 suites failed in 626s** on a tree that
differed from the cut's green run by a single markdown file. It was not a regression: the first failing

**Two things worth reading off that rather than the total.** The leg that cost the most was not work; it
was a gate that could not be trusted to mean the same thing twice, which is the most expensive kind of

finished correctly -- the tag, the documents and this page are all where they should be -- which is the
argument for measuring a release rather than estimating it: an estimate written afterwards would have
recorded a routine cut.

## What was still open at this release

**One issue stood open when this was cut**, filed ten minutes before the clock started:
[#1032](https://github.com/DaveKJohn/claude-code-specialists/issues/1032), an inbound report that
`team-shopify`'s live-theme guard blocks *authoring* a script that merely contains a theme delete -- and
that its own refusal text advises forging the marker that would get past it. It was not picked up here, so
it ships in a later release. If you run that guard, expect it to refuse an edit to a script rather than an
actual delete.

**Two properties were left as they are, deliberately, and both are worth knowing.** The gates read your
branch's own document rather than the diff -- this release closed the one shape that let an uncommitted edit
through, but the general property is unchanged and intended, so **you** are still the one who commits your
work. And the label seam deliberately does not reach the lint and test gates: those live in `open-pr.ps1`,
and calling them from the sync would couple `team-shopify` to `contributing-davekjohn`. A repo that wants
the gates runs the sync with the merge seam off and opens the PR through its own route, which is what the
default already does.

## Correction to this page

**2026-08-28, hours after publication.** Two statements in *What this release cost to cut* were falsified
the same evening, while [#1033](https://github.com/DaveKJohn/claude-code-specialists/issues/1033) -- the
inbound report this release's own gate trouble produced -- was being verified. Both have been corrected
above and both are set out here, because a reader who acted on either would have acted wrongly.

**The 443s was a load reading, not a cost.** The page first said *"The suites are now the release, at 443s
of a 10m freeze"*, and named that leg *"the leg to watch, because it is the only one that grows with the
product"*. Five full `Invoke-TestSuiteGate` runs on the same tree, all **54/54 green**, put the gate at
about **200s**: 194s at 16 lanes, 216s at 18, 203s at 18 under a UTF-8 console -- and **421s** and **419s**
with a second identical gate running beside it -- a pair that reproduces this release's own 443s to within
5%. So the figure was never the suites' cost; it was a reading of what else the machine was doing, and the
conclusion drawn from it overstated that leg by more than a factor of two.

**The red run did not depend on who invoked the gate.** The page first said *"The verdict had depended on
who invoked the gate, not on the tree."* It does not: `cut-release.ps1` dot-sources `repo-config.ps1` and
`native-capture-lib.ps1` (lines 262 and 275) before it calls the gate, so the green run inside the cut and
the red run driven from the session afterwards had **identical** state. What is left is real but older than
this release -- red under the gate and green alone has now been seen three times on these suites, and none
of the three reproduces. It is named where it fires, in `Invoke-TestSuiteGate`'s own docstring, rather than
attributed to a mechanism that does not exist.

**Three things are deliberately not done here.**

The **`443s` in the timing table is left exactly as it stands.** That leg did take that long, and recording
elapsed time is the row's whole job -- it was true when it was typed, and
[the published-record rule](../../../../plugins/dkj-policy/RELEASES-portable.md#once-it-has-landed-it-is-a-published-record--and-that-protects-only-what-was-true)
protects exactly that. What the rule does not protect, and what was corrected, is the *claim about the
gate's cost* built on top of it. The two are easy to run together; the table records a clock, the paragraph
made an argument.

The **paragraph calling this a gate that could not be trusted to mean the same thing twice stands**, because
it is still true. The re-measurement removed the explanation, not the symptom.

The **copy attached to the GitHub Release is not replaced**, and here the two halves reached readers
differently. `v4.22.0-notes-for-users.md` was uploaded at 15:19:17Z and carries the 443s claim in its
first, uncorrected form. It does **not** contain the caller attribution at all -- that sentence was written
into this page afterwards, in the release-notes commit, so the asset still ends its timing section at
*"the total is added in a second pass"*. **This page is the current version**, and the asset is not.

The full re-measurement, with the run table and the machine state beside each figure, is in
[the performance lens that holds this repo's timing measurements](../../../../.claude/specialists/lenses/specialist-06-25-lens.md#a-gate-verdict-that-moves-is-a-load-reading--n5-and-the-caller-is-not-a-variable-august-28-2026).
The report that prompted this correction is
[#1038](https://github.com/DaveKJohn/claude-code-specialists/issues/1038).
