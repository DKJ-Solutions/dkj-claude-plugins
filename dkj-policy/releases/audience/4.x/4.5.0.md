# Release notes v4.5.0 🚀

**Date:** 2026-08-11  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

Ten of the fifteen changes in this release reach you, and most of them are the same repair: a gate or a
document that pointed at something which is not there.

## For consumers

**One thing to check, one thing to correct in your own repo, and the rest arrives for free.** No command
changes its name, no seam function is renamed, and nothing you have written becomes invalid.

### 1. `open-pr -RefreshBody` no longer deletes the rest of your PR template

If your `.github/pull_request_template.md` has more than one section, `-RefreshBody` deleted **everything
below the description** and then reported success, naming only the description. The more sections your form
has, the more went missing; a single-section template loses nothing, which is why this survived as long as it
did.

**Update, and check any pull request whose body you have refreshed** — the deletion was silent and nothing
recorded what was removed. `open-pr` now also warns by name when a heading vanishes from a body, which after
this fix should be unreachable; it is kept as a tripwire for the next shape nobody predicted.

### 2. If you have run `adopt-config`, one comment in your `repo-config.ps1` is wrong

`Get-ReleaseConsumerBumps` used to mean *"which bumps also get a consumer document"*. It now means *"which
bumps get the hand-written release note **at all**"*. Your **value** is unaffected — `@('minor','major')` was
correct before and is correct after — but `adopt-config` copies the blueprint's explanation **verbatim** into
your own `scripts/repo-config.ps1`, so the sentence sitting in your repo today explains a directory the
script will never write.

**Re-run `adopt-config`, or edit that one comment by hand.** Two knobs are also documented that never were:
`Get-ReleaseNoteWording` and its nine keys, and the fact that they are **not** the same set as
`Get-InternalNoteWording`'s eleven. Overriding by the wrong list configures a flow you are not running.

### 3. The changelog-entry gates now tell you what is actually wrong

Three refusals were pointing at things that do not exist:

- a tier reason written **below** its `**Score:**` line was refused as *"a tier with no reason"* — the one
  claim you can see is untrue while looking at your own three written paragraphs;
- the same misdiagnosis reached `cut-release`, which meets you days later, when you are no longer the person
  who wrote the entry;
- and the ranking gate asked you to *"fill in the third column"* of a table this entry format replaced. Your
  file is made of headings. It has no columns to count.

All three now name the shape your entry actually uses, and point at the `**Score:**` line. You are also told
**before** you write rather than only when you are blocked: `new-branch` prints that the reason goes above
the score line, and the guidance in `branch/templates/` says the same.

**No action needed.** The older impact-table and `Tier: N` shapes are still read, and still get their own
wording — a real table has three columns, so that advice stays correct there.

### 4. New: the rules for working from somebody else's ticket tracker

`workflow-davekjohn` now ships
`TICKETWORK-portable.md`, covering the
layer *before* `new-branch` — where work reaches you from a tracker as a desired outcome rather than an
instruction. Ten rules, each with the instance that produced it. The sharpest: the test is *"can we build what
they ask"*, not *"is it a good idea"* — two questions, and only the first is yours before starting. That one
unblocked three of six real tickets, one of them after seven weeks.

**Rules only — no template, no skill**, deliberately, and the page says why in a closing section so you read
the absence as a decision rather than an oversight. One trap it names because you will meet it: ticket files
sitting in your repo root as `*.md` look like unfolded changelog entries to the release cut. Put them in a
directory, or list them in `Get-ReservedRootMd`.

### 5. Timing a release is a two-pass job, and the checklist now says so

Step 0a asked for the end-to-end duration in the release note — a number that document structurally cannot
hold, because it is frozen for its own pull request while the merge and the publish are still running on that
very file. At the previous release the part measurable at freeze was **9m 42s** of **28m 03s**: the
unmeasurable tail was two thirds, and the predictable failure is filling that gap with an estimate in the one
section whose point is that the figure was measured.

The checklist now asks for the subtotal and the blocking split at freeze, and the total afterwards in its own
small pull request. **No action needed** — this is a convention, not a gate. What following it buys you is the
one number that cannot be recovered afterwards.

### 6. Ask what something costs and get a distribution, not one run

Your performance engineer carries a new rule: **a cost that varies per run is counted over its population,
not cited from one run.** It lives in
[his manual](../../../../plugins/dkj-subagents/dkj-subagents-alpha/manuals/specialist-06-25-manual.md), so it applies to every cost question
you put to him, not only to releases.

The instance behind it: a CI figure taken from one carefully measured run and quoted correctly turned out to
sit **exactly on the p90** of all 63 runs — the slow tail recorded as the typical. Accurate and
unrepresentative are not the same property, and only one of them is visible while you hold a single sample.
You should now get an n, a median and a range, and a plain statement of whether the conclusion moved.

### 7. Documents that described a retired model have been corrected

`releases/README.md` still described the three-document release model four days and two releases after those
documents were merged into one note with a named section per reader. Corrected, along with two smaller claims
on the same page: the GitHub Release body is generated rather than lifted from a hand-written note, and the
release-history row's link is written by the cut itself.

**Nothing to do** — the published release list is untouched.

## What it is worth

**Eleven of the fifteen changes are one defect wearing different clothes: something that named a thing which
is not there.** A gate asking for a column in a format made of headings. A gate calling a written reason
missing. A blueprint describing a directory the script never writes. An overview page describing three
documents where there is one. A checklist asking for a number its own document cannot contain. Not one of
them broke a build, and every one of them cost somebody time while looking authoritative.

**What this release is worth is the naming, not the ten repairs.** The rule it makes explicit is that a
gate's *wording* is part of its correctness. A refusal is the only part of a tool that speaks to somebody who
is already stuck, and one that points at the wrong thing does worse than stay silent: it sends them to check
something that cannot be wrong, and what they end up distrusting is the gate rather than the message. Two of
these were found by consumers who had to read the library line by line to learn why they were being refused.
That cost is invisible to every test suite involved, because all of those gates were passing their own tests.

**The second thing worth recording is where the reports came from.** Four inbound issues close here, three of
them filed by a consuming repo rather than found in this one — and two could not be reproduced here at all,
because this repo's own PR template has a single section and its own entries were already in the current
shape. A source repo cannot measure the defects that exist only downstream. What surfaced them is a consumer
filing an inbound issue instead of working around it quietly, and that mechanism earned its keep three times
in one release.

**Both numbers the last release left open were counted.** Nine of the thirty suites read this repo's own
markdown, which is what decides whether a markdown-only diff has room to skip anything; and the release
cadence was counted against the fixed gate cost and then deliberately left unconstrained. Neither became a
gate.

**And one honest gap: this release was not timed.** Step 0a shipped one release ago and was not followed
here — no clock was noted before the cut, so there is no total and it cannot be reconstructed. What can be
proven: the cut's own gate ran 30 suites in **223s**, the pull request ahead of it waited **8m 55s** on CI,
and `lint-en-tests` across the last seven completed runs has a median of **8m 57s** over a range of **6m 11s
to 13m 30s** (n=7). That last figure is the population form of the very number this release added a rule
about — a single-run citation here would have read 8m 55s, near the median by luck, and would have been
wrong by four and a half minutes had the 13m 30s run been the one in hand.

## What was still open at this release

- **#596's structural half sat with Dave, unbuilt.** Making a reason-below-the-score impossible rather than
  well-signposted needs either the sub-section inverted to score-then-reason, or the reason given its own
  label. Both change the entry format that folds verbatim into `CHANGELOG.md` and travels outward, and both
  need the parser to read the old and new shapes side by side. The recommendation at this release was to
  close the question rather than build either form.
- **`fold-changelog-entry.ps1`'s docstring still described the impact table** — one row per tier with the
  significance in its second column — and still named the retired `### Who is this for` heading. The same
  class as the gate repaired in this release, one layer further in: a developer reading the source rather
  than an author meeting a refusal. It sat with the technical writer.
- **The drafted consumer section still carried one line of branch language per change**:
  `#### What does the change on this branch bring to main?`, inside the section written for a consumer.
  Reported at v4.3.0, again at v4.4.0, and still not repaired — it is draft noise the writer deletes while
  rewriting, and closing it properly needs a heading-only remover nobody has asked for.
- **The GitHub Release was published before this document's pull request**, the reverse of the checklist's
  step 4 then step 5. The generated body was correct and needed no editing, so nothing was published wrong;
  what that ordering exists to prevent is a Release page pointing at a note that is still a draft, and for a
  short while that is what it did.
- **The release was not timed**, as above. The convention had run once when this was written, and was then
  skipped at the next opportunity — which says something about a convention that depends on remembering an
  action before the first command.
