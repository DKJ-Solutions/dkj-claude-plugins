# Release notes v3.2.0 🚀 — one product, one marketplace

**Date:** 2026-08-03  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

**This release renames the marketplace, so every existing installation needs one action.** Nothing
about that will announce itself: a session whose marketplace name no longer resolves does not error —
it simply loads no specialists at all. Read the first section before updating; the rest is what you
gain once you have.

## For consumers

### Act on this first — the marketplace was renamed

`davekjohns-workshop` is now **`claude-code-specialists`**, matching the repository name. Marketplace
and repository having different names meant remembering forever which one lived where, which is
exactly what bites while debugging a plugin that will not load.

**What this breaks, and how quietly.** Your `.claude/settings.json` names the old marketplace and the
old plugin IDs (`specialists@davekjohns-workshop`). Your install record is keyed on the old ID too.
None of that produces an error message — Claude Code resolves nothing, reports nothing, and the
session starts normally with no subagents, no skills and no hooks. If your orchestrator suddenly
sounds generic, this is why.

**Two keys and one ID change.** In your repo's `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "claude-code-specialists": {
      "source": { "source": "github", "repo": "DaveKJohn/claude-code-specialists" }
    }
  },
  "enabledPlugins": {
    "specialists@claude-code-specialists": true
  }
}
```

Then remove the install record that still points at the old ID, and re-install under the new one —
from your repo's root, once per plugin you had enabled:

```powershell
claude plugin uninstall specialists@davekjohns-workshop --scope project
# restart your session, then:
claude plugin marketplace update claude-code-specialists
claude plugin install specialists@claude-code-specialists --scope project
# restart once more
```

The full procedure, with every failure mode, is **[QUICKSTART.md](https://github.com/DKJ-Solutions/dkj-claude-plugins/blob/d0df1db2c0b4489bf311337430c215d47255b78e/INSTALL.md)** — it works
as a migration path unchanged, since the old registration disappears the moment its settings key does.
**One honest limit:** the sequence above follows from the documented mechanics rather than from a
measured migration of an existing consumer, so verify with the query in QUICKSTART Step 6 rather than
trusting a `Successfully installed` line, which names no version at all.

**And if you renamed your local checkout folder to match, that unlinks the install by itself.** The
record is keyed on the folder path, so a rename leaves it naming a directory that no longer exists —
again with no error. Same repair: re-install from the new path.

### What you gain

**Shorter paths, one level less nesting.** The plugins moved from
`claude-code-plugins/claude-specialists/<plugin>/` to **`plugins/<plugin>/`**. If your `CLAUDE.md` or
seam carries a hard-coded import path into the plugin cache, it moves with this — every path in the
repo lost 31 characters. The persona import now reads
`~/.claude/plugins/marketplaces/claude-code-specialists/plugins/specialists/personas/01-01-persona.md`.

**A dead persona import is now loud instead of silent.** This is the failure above, generalised: the
orchestrator's body is the one part of the system that comes from outside your repo, through a single
`@`-import. If that path is wrong, the session still starts, your roster still renders — and the
orchestrator runs with no ritual and no delegation discipline. Nothing reported it. The roster check
now resolves every import and raises an error for any that does not exist, naming the path so you can
look it up. It stays an error when the cause is "the plugin is not installed on this machine", because
that is precisely the state in which your orchestrator has no body.

**Three more scripts you could not reach before.** `ship-pr.ps1` (open a PR, wait for CI, merge, fold
— previously hand work in every consuming repo), `verify-resolved-issues.ps1`, and
`fix-mojibake.ps1`. Two things are configurable rather than assumed: your merge method
(`merge`/`squash`/`rebase`, validated before it reaches `gh`) and which files the mojibake check walks.
Its fallback is now every `*.md` in your repo root — including an unfolded changelog entry, the
freshest and most accent-carrying file in any repo using this flow, which the old hard-coded list never
covered.

**Changelog stub wording is yours now.** The shared entry scaffolder wrote four English strings into
every entry file. They are read from your own `repo-config.ps1` if you define them, so a
non-English-language repo no longer has to keep a private copy of the whole script to change four
values — which is how one consumer ended up with two entry formats for a single branch, depending on
which entry point ran.

**The release cut is shared, and can write for three audiences.** Everything that legitimately differs
per repo — which root docs are permanent, how notes are foldered, the category labels, whether there is
a plugin tier at all — is read from your config, each with a fallback to previous behaviour. A stakeholder
document for non-developers is now generated too, if you switch it on.

### What was repaired

**A release card no longer tells you where you are.** Every plugin's `RELEASE.md` said *"You are on
this release."* — written when the release was cut, about a reader it has never met. In the ordinary
case it was false: the documented update path installs from `main`, so you are typically several commits
past the tag whose number the card carries. It now states the version its manifest holds and hands the
"where am I" question to the check that can answer it.

**The teardown stopped contradicting itself.** Re-running the audit after uninstalling used to report
that the plugin install was "untouched" one step after `Successfully uninstalled`, advising a command
you had just run. It now reads the install record first and has three answers, because *"no record"* and
*"could not look"* are different claims — and when a record does point at your repo, it names the scope
that record is actually in rather than assuming `project`.

**The uninstall guide's disarm promise is now conditional, and the condition is the point.** It claimed
that walking to the end of Step 5 disarms the mechanism "stray key or not". Measured: after a
by-the-book teardown with both keys deliberately left behind, two session starts and no commands at all
put the machine back on an install record. What actually disarms it is Step 3 removing
**`extraKnownMarketplaces`** — that is the key that can put the marketplace back, and everything else
follows from it.

**Four per-plugin `CHANGELOG.md` files still named the old marketplace** in a sentence describing the
present mechanism, in the most consumer-facing file each plugin has. The intro is written only when the
file does not exist yet, so every later release appended below it and never revisited it — the template
had already been corrected and the correction could not arrive. It is generated from the manifest now,
and a gate holds all four to it.

### Where to start reading

**`QUICKSTART.md` is now genuinely short** — two settings keys, four commands, one verification query,
two restarts, about four minutes. The thorough, measurement-backed manual it used to be is
**[ADOPTION.md](https://github.com/DKJ-Solutions/dkj-claude-plugins/blob/d0df1db2c0b4489bf311337430c215d47255b78e/INSTALL.md)**, which states its own reading time at the top: ~44 minutes,
plus ~27 for the bootstrap skill's own page. That number is the one a first-time reader plans with, and
the page never used to give it.

Three things ADOPTION.md now covers that it did not:

- **Filling your lenses is Step 4, not a closing aside.** It used to be disclosed in a trailing clause
  reading *"then, at your own pace"*, which is how one owner came to blame the installer for half an
  hour that was actually authoring. The bootstrap places the whole seam in seconds; the time goes into
  saying what each specialist serves in *your* repo. An unfilled lens does nothing.
- **Where a delegated adoption has to stop.** If you hand this page to an agent: of Step 1's six acts it
  can do four. The two session restarts it structurally cannot, because it runs inside the session it
  would restart — and Steps 2 through 4 follow from that. The table says who does what, and what the
  agent should hand back.
- **The second-adoption state.** If this machine has adopted the family before, a leftover user-scope
  marketplace registration makes part of Step 1 silently unnecessary, the usual failure message never
  appears — so its absence proves nothing — and your repo's own `extraKnownMarketplaces` key is never
  exercised at all. A mistyped slug then survives every check on the page. One extra line closes it:
  after the refresh, run `claude plugin marketplace list` and confirm the entry came from your repo's
  settings.

Adoption remains reversible by design: **[UNINSTALL.md](https://github.com/DKJ-Solutions/dkj-claude-plugins/blob/d0df1db2c0b4489bf311337430c215d47255b78e/UNINSTALL.md)**.

## What it is worth

This release has two halves. One is a rename and reorganisation that every existing user has to act on
once. The other is the quieter and more valuable half: work that existed three times now exists once,
and four checks that reported "fine" without looking have been repaired.

- **Maintenance that was paid three times is now paid once.** The release and review workflow was
  duplicated across projects; an improvement had to be made in each of them, or the copies quietly drifted
  apart -- which is exactly what had happened. From now on an improvement reaches every project through an
  update instead of through repeated manual work.
- **Less false confidence, which is the expensive kind.** A check that reports a problem costs an hour. A
  check that reports success without looking costs whatever is built on top of it before anyone finds out
  -- and nobody goes looking behind a green result. Four of those are gone.
- **Someone can start using this without help.** The installation page was thorough and therefore
  unusable as a first step; it is now split into a short path and a reference. Three separate people
  getting stuck in the same place is what prompted it.
- **A working rule was written down that had cost real repairs.** A report says both what went wrong and
  why, and the second half is a guess by whoever measured from the outside. Acting on that guess produces
  a fix that satisfies the report and is wrong -- which is worse than the original problem, because it now
  carries a justification. The reason gets verified first.

## What was still open at this release

- **Every existing user has to reconnect once, and this is the one item that needs action rather than
  reading.** The rename means installations point at a name that no longer exists. Nothing errors -- it
  simply stops loading -- so this is documented rather than fixable from our side. No release can do it for
  them. **The steps are in the user-facing notes attached to this release.**
- **The user-facing version of these notes is written** (it was still a generated draft when this summary
  was first filed). The automatic split between "what a user notices" and "internal detail" had put the
  three most important items on the wrong side in this particular release; that is now corrected in the
  document and written down as a standing warning rather than trusted. It is attached to this release
  alongside the full technical record, and it is the one to read if you have to reconnect.
- **One project still runs its own copy of the release tooling** until it picks up this version. The
  duplication is removed at the source; the last step is on that side.
- **One reported observation is deliberately not acted on.** It was seen once and has not been reproduced,
  and the report asks for reproduction first. Repairing an unreproduced symptom is how the wrong cause
  gets a citation.
- **One known cosmetic defect in generated release notes is unresolved.** It is recorded where the next
  person will meet it, with what has and has not been ruled out; the cause is not isolated yet.
