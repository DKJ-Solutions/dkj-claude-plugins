# Release notes v3.10.0 🚀

**Date:** 2026-08-09  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

**Every plugin in this family was renamed, and every existing install breaks until you reinstall
under the new names.** Nothing fails loudly — the old ids simply stop existing in the marketplace —
but nothing carries over on its own either.

## For consumers

### Reinstall under the new names

| old plugin id | new plugin id |
|---|---|
| `specialists` | `team-alpha` |
| `specialists-lifehub` | `team-lifehub` |
| `specialists-shopify` | `team-shopify` |
| `specialists-ecomm` | `team-ecomm` |
| `specialists-workflow-davekjohn` | `workflow-davekjohn` |

Full command sequence, including the refresh step that has to run first:
[Migrating from the old plugin names](https://github.com/DKJ-Solutions/dkj-claude-plugins/blob/d0df1db2c0b4489bf311337430c215d47255b78e/INSTALL.md#migrating-from-the-old-plugin-names)
in `plugins/INSTALL.md`.

**Read that section before you run a single command — there is a choice in it that a mechanical
rename will not surface for you.** If you never enabled `specialists-workflow-davekjohn`, the table
above gives you back every team you had and leaves you with **no workflow enabled at all**, because
none of your old ids was one. Nothing about your session will announce this afterwards: your
specialists keep answering, and a question that did not use to exist (see below) now sits
unanswered. Decide on purpose whether that is what you want, or whether you want `workflow-default`
(see the next section) instead.

### Every plugin is now a team or a workflow

A **team** is who the specialists are; a **workflow** is how work moves through the repo they land
in. That distinction was already true of what these plugins did — it is now what their names say.
The practical rule: **teams stack, a workflow does not.** Enable the core team plus whichever add-on
teams fit your repo. Enable **exactly one** workflow. Two workflows would answer the same questions
(how a branch is named, how a change reaches the trunk, what a release is) differently, with nothing
saying which answer is yours — so if you do end up with two enabled, the core team now reports it at
session start rather than silently picking one.

### A workflow for a repo that has not chosen one

New plugin: **`workflow-default`**. It carries no method of its own — where `workflow-davekjohn` is
one particular branch/changelog/release model, this is the deliberate absence of one, so that
absence is something you can enable rather than a gap you have to fill in yourself.

It ships one skill, **`discover-workflow`**, which reads what your repo already does — branch names,
commit style, how a change reaches the trunk, what gates it, whether your process is written down —
and records the answer in one file. Where your repo has not settled something, the skill says so
plainly instead of guessing or importing a habit from elsewhere; a silent guess there would be worse
than an honest gap. The file is never overwritten on a later run, so anything you correct or add by
hand stays.

`workflow-default` is enabled by default alongside the core team for a first-time install. If you are
migrating an existing install and did not run `workflow-davekjohn` before, this is the plugin that
gets you an explicit answer instead of an unannounced blank one.

### Smaller repairs in this release

- **The `adopt-config` skill page stops sending you to the plugin author's own disk.** It printed both
  of its commands as an absolute path into a specific Windows user account — wrong for every reader,
  and it shipped that way in both v3.8.0 and v3.9.0. It now uses the same portable form as every other
  skill page.
- **A health check now tells you when an enabled plugin has no install recorded for your repo.** Until
  this release that state produced no warning at all: a session would run with none of that plugin's
  specialists — no skills, no subagents, no hooks — while everything else looked normal. This is the
  scenario a mid-session update across this very rename can produce, so check for it if your session
  was already open while you migrated.
- **The startup check that reports plugin versions now says which commit it read them at.** If your
  session has been open for a while and you pull in updates mid-session, the version line you see can
  otherwise be hours stale without looking like it.
- **The pull request template for contributing to this repo dropped sections that only restated the
  changelog entry a few lines below them.** Relevant if you open pull requests against this source
  repo; it changes nothing about using the plugins themselves.

### Before you update

A `github` marketplace source is a cached clone, and an install compares against that cache rather
than against what was just tagged. Refresh first, always:

```powershell
claude plugin marketplace update claude-code-specialists
```

## What it is worth

> **If you run this product in a repo, this release requires you to act.** Every plugin was renamed, so
> every existing installation stops resolving until it is reinstalled under the new names. What to run,
> in what order, and the one choice a straight rename will not surface for you, are in full in
> `plugins/INSTALL.md`, under *Migrating from the old plugin names*.

**The naming was costing a decision every time somebody added to this product.** One prefix covered two
unrelated kinds of thing, so "what is this new plugin?" had to be looked up rather than reasoned about,
and the answer lived in a table that went stale. It is now a question with two answers, and the answer
picks the name. That is the durable half.

**The reinstall is a one-off cost, paid once per connected repo, and it buys the rest.** Three repos are
connected today; a fourth would have paid the same cost later at a worse moment, because this kind of
rename gets more expensive with every consumer added, never less.

**The largest reduction in dependence on a developer is the one that is easiest to miss.** Five scripts
each kept their own answer to "which plugins exist and where do their folders sit", each encoding the
directory layout. Adding or moving a plugin meant finding all five and hoping. They now read one source,
which is why the directory reorganisation in this same release needed **no production script change at
all** -- measured: the move produced 45 findings, every one a dead link in a document.

**And a class of defect that used to reach consumers is now stopped before it ships.** A skill page that
printed the author's own disk path went out in two consecutive releases; the page was the instance, and
this release added the gate that refuses the class.

## What was still open at this release

*A snapshot of 2026-08-09, not a claim about the present.*

- **The three connected consumer repos had not migrated yet**, and their register entries still name the
  old plugin ids on purpose -- the register records what a consumer has, so writing the new id early
  would report a real migration as missing. The next step sits with whoever runs each of those repos.
- **A second checkout of this repo, on another machine, was still on the old plugin ids** at the moment
  this was cut. Its owner does that migration when it suits them.
- **One caveat is documented rather than repaired**: a consumer whose repo lenses still sit on the older
  of the two supported locations has the plugin name inside that path, so their lenses go unseen after
  reinstalling under the new name. No connected repo is confirmed to be in that state, and the fix is
  renaming one directory. It is written down in the migration page rather than pre-empted in code.
- **This release is `3.10.0` and not `4.0.0`, and that was decided rather than defaulted.** The rule here
  is that a major *recaps* ten minors; this line had nine. The work is breaking for consumers, which is
  the usual argument for a major, so the rule and the instinct genuinely pointed different ways. The
  rule won, and the next release can be the major without overruling anything.
