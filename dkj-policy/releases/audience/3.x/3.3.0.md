# Release notes v3.3.0 🚀 — the release process, from three sides

**Date:** 2026-08-04  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

**Nothing in this release requires action before updating** — but two things change behaviour, so read
those before you next open a PR or cut a release. If you are still on the old marketplace name, that is
`v3.2.0`'s change and it has not gone away: read [that release's notes](3.2.0.md) first, because nothing
will report an error at you.

## For consumers

### Two changes in behaviour

**A PR is now refused while its changelog entry still carries the scaffolder's own wording.** If your
entry file still has the placeholder title, the "to do / where I left off" heading, or the fallback body,
`open-pr.ps1` stops before the lint, the tests and the push, and names what it saw. Fenced code is
excluded, so an entry that *documents* this mechanism is not accused of it, and `-Force` is the escape
valve — deliberately separate from `-SkipLint`/`-SkipTests`, because it overrules a judgement about
content rather than skipping a tool.

This is a repair, not a precaution. In the release before this one, three entries kept that heading with a
status appended behind it and reached the release notes **and** the per-plugin `CHANGELOG.md` files that
travel to you in the plugin cache. The window closes at the merge and it closes invisibly: the fold moves
the entry into `CHANGELOG.md` and the next release moves it on into `releases/`, so by the time anyone
would look, the place to look is the one place it no longer is.

**The highlights tier no longer produces a print-ready `.html`.** Markdown only, in every consumer — this
is a removal from the shared code, not a knob switched off upstream. If you have the tier enabled and were
relying on that file, your next cut produces markdown alone. Existing `.html` files under
`releases/highlights/` are your repo's history and are left alone.

Removing it is an improvement rather than a subtraction: the renderer handled a partial markdown subset and
passed links through as their own literal source text — documented as a known limitation and pinned by a
test asserting the limitation stayed. A page that silently renders a link as `[text](url)` is worse than no
page. For a PDF, render the markdown with a tool built for it.

### What you gain

**A third release tier, and a script to write it.** `new-internal-note.ps1` writes
`releases/internal/<dir>/<X.Y.Z>.md` — a short summary of *what the work is worth*, for colleagues,
employers and management. It takes the development notes as its input, so it runs **after** the cut; the
cut prints the invocation for you and gates that line on the script being present, so a repo without the
tier never sees it.

**It is the tier that covers a patch, and that is the point.** The three tiers answer three different
questions: the development notes are the per-PR record, the highlights are *what a user notices*, and this
one is *what the organisation gets out of it*. They come apart most clearly on a patch — a release with
nothing for a user can still be the one where a routine change stopped needing a developer. So the internal
note is written at every release, while highlights stay minor/major only. It refuses to overwrite an
existing note without `-Force`: it is the one document of the three that cannot be regenerated from
anything.

**The release checklist has a fixed body rule and a corrected order.** The GitHub Release is now the *last*
step, after the written documents have merged — not the second, directly after the tag. That was a real
error rather than a preference: once the body can be a document written after the cut, publishing from step
two publishes a body that does not exist yet. The body itself is the highest tier your repo actually has —
internal note, else highlights, else the development notes — with every other tier attached. Never inline
the development notes: `gh`'s body limit is 125,000 characters and a real notes file exceeds it.

**Which bumps get a Release is yours to decide.** It used to be stated as minor/major-only in the shared
checklist; it is repo policy now, because a repo publishing at every release and one publishing at
minor/major only are both coherent, and the choice follows from who reads the page.

### Worth knowing before you edit a highlights draft

Two things this release measured, both of which cost time if you learn them the hard way.

**The `Feat`/`Fix` marker is a proposal, not a verdict.** The generated draft puts those above the
"remove before publishing" marker and everything else below. In a storefront repo that split is reliable —
a `Style` branch there *is* a customer-visible change. In a tooling repo it is not: in the previous release
the single most consequential change for a user, a rename that breaks every existing install with no error
message, arrived on a `chore/` branch and therefore landed below the marker at line 1,034 of 1,098. Read
both halves and promote what matters; do not simply delete the bottom one.

**Budget for a rewrite, not a trim.** The tier renders the release a *second time* — it does not translate
it. The draft is the same prose the development notes carry, regrouped, so turning entries written for
someone reviewing a diff into a document for someone deciding whether to update is an authoring job.
Measured on the first one: 1,098 draft lines became 153.

Updating is the usual two commands per plugin, from your repo's root — the refresh first, because an
`install` does not perform it:

```powershell
claude plugin marketplace update claude-code-specialists
claude plugin update specialists@claude-code-specialists --scope project
```

The version number is not the code: the clone these commands read tracks `main`, not the tag. Full
detail in **[ADOPTION.md](https://github.com/DKJ-Solutions/dkj-claude-plugins/blob/d0df1db2c0b4489bf311337430c215d47255b78e/INSTALL.md#staying-up-to-date)**; the short path is
**[QUICKSTART.md](https://github.com/DKJ-Solutions/dkj-claude-plugins/blob/d0df1db2c0b4489bf311337430c215d47255b78e/INSTALL.md)**.

## What it is worth

This release is about the release itself: who it is written for, and what can no longer escape into it.
The previous one shipped unfinished placeholder text to the documents customers receive; that is now
impossible, and the same release is the first that reaches a non-developer reader on purpose.

- **The work becomes visible without anyone having to summarise it afterwards.** There is now a page per
  release, written for people outside the team, produced as part of finishing the release rather than as a
  separate favour later. The version that used to be skipped -- the small releases -- is exactly where the
  quiet improvements live.
- **Less risk of an embarrassing detail reaching a customer.** The escaped placeholder text was not
  discovered by a review; it was found afterwards, in files that had already been distributed. A review
  that has to catch this every time will eventually miss it once, which is why it is a refusal now instead
  of an instruction.
- **Editing the user-facing version is now a known quantity.** The first one took the generated draft from
  roughly eleven hundred lines to a hundred and fifty, and the most important item for a user turned out to
  be near the very bottom. That is written down as an expectation, so the next one is an hour of editing
  rather than an open-ended question.
- **Our own documentation became more trustworthy, which is worth more than it sounds.** Four separate
  documents turned out to be correct when written and wrong when read -- a stale rule, an overtaken plan,
  two outdated claims. None of them were mistakes at the time. The habit that catches this is now a step in
  the procedure instead of a matter of care, because care does not scale and steps do.

## What was still open at this release

- **The previous release had no public page yet at the moment this was written.** It has one now; the two
  small releases before it fall under the old rule and are deliberately not filled in after the fact
  unless that is asked for.
- **Anyone still on the old product name has to reconnect once.** That was the previous release's change
  and it has not gone away: installations point at a name that no longer exists, nothing reports an error,
  it simply stops working. The steps are in the previous release's user-facing notes and in the project's
  own adoption guide.
- **One project still runs its own copy of the release tooling** until it picks up this version. The
  duplication is removed at the source; the last step is on that side.
- **Two known defects are deliberately untouched** because their cause has not been established. One has
  been seen once and never reproduced; the other reproduces only in isolation and not against real data,
  and does not yet have a record of its own -- which is the cheapest first step available here.
- **One abandoned piece of work is still stored remotely** and needs removing by hand, deliberately: that
  deletion is not something the team automates.
